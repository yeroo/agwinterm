## The vocabulary, fixed before anything is written

agterm's command reference (agterm.com/commands, read 2026-09-06): `session split [on|off|toggle]
[--axis vertical|horizontal]`. **`vertical` produces left/right panes — today's only layout;
`horizontal` produces top/bottom panes.** Omitting `--axis` keeps the current orientation, and a
session that has never been split defaults to `vertical`. `session focus` takes
`primary|split|left|right|top|bottom|other`; `session resize` gains `--grow-top` / `--grow-bottom`
beside `--grow-left` / `--grow-right`. This repo contradicts itself today (`agliteterm/src/main.cpp:6`
calls the side-by-side split "vertical" — agterm's word; `docs/agterm-gap-analysis.md:47` calls it
"horizontal"), so the word is stated **once** in `ISessionHost.Split`'s comment, once in
`AgentSkill.cs`, once in the CLI usage header, and the gap-analysis line is corrected. The axis
names the **arrangement**, never the divider.

Two divergences from agterm, recorded here and in `docs/agterm-parity.md`, not silently:

- **`off` destroys the split shell** (agterm hides it and keeps the process). Already recorded in
  the tracker; unchanged by this batch. `session split close` is therefore the same destruction
  with a pane target — its new capability is closing **either** side (see Overview).
- **A swap moves panes, never ids.** agterm's swap moves the session's public identity to the other
  shell (its panes are addressed by role, `primary|split`). Ours are addressed by **id**, and an
  agent holding a pane id must keep reaching the same shell after a swap. So a swap reverses the
  pane order, keeps the geometry (axis and ratio sequence), moves focus with the pane, and leaves
  every id where it was — the session id keeps naming the pane it always named, which now sits on
  the other side. That relaxes one invariant: "the first pane shares the session id" becomes
  "exactly one pane carries the session id", and `CreateSession` / restore must accept a pane-0 id
  that differs from the session id (Task 5).

## Overview

Four items on one subsystem — a session's two panes — plus the reply that makes them scriptable.

- **`session split` returns the pane id.** Today it answers the constant `"split"` from a
  `Post(...); return true;` (`Program.ControlHost.cs:491-501`), so the caller cannot address the
  shell it just created (lite returns the id, `agliteterm/src/main.cpp:7911-7947`, and the parity
  tracker calls this a gap inside our own family). The host moves to `InvokeOnUiQueued` so the id
  names a pane that exists; **`on` when already split returns the existing split pane's id**
  (lite's rule: a caller that does not know whether it split gets something addressable either
  way); `off` returns the surviving pane's id; `toggle` returns whichever it produced. A bare
  string, so the conformance step (`control-api.json:284-292`, `"result":"string"` on `split off`)
  keeps passing on the type check it makes.
- **An axis.** `session split on --axis vertical|horizontal` (and `toggle`); a session's axis is
  per session (`Ses.Axis`, default vertical), survives restore as an additive `SessionState.Axis`
  key validated on load, and is reported by `tree --json` as `"axis"` inside the `paneCount > 1`
  block — always, like `focusedPane`, because absence would mean "this build has no axis", which
  tells a caller nothing. `--axis` on an already-split session **re-orients it live** (agterm:
  omitting the flag preserves the orientation, so passing it sets it). The layout has one source of
  truth (`PaneLayout`, `Program.Sessions.cs:453-469`) and ~20 sites that assume columns — the list
  in Context is the task's checklist.
- **`session split close [--target <pane id>]`** — closes the targeted pane, **either side**; the
  survivor becomes pane 0 with the full width/height and focus. No target, or a session id → the
  session's focused pane (what `Ctrl+Shift+W` does). A single-pane session is **refused**
  (`session close` is the verb for that; a `split close` that closes a session is the silent-success
  class). Reply: the survivor's id. The tracker says this item is "naming, not behaviour" — it is
  not: no control verb can close pane 0 of two today (`off` hard-codes `Panes[0]` as the survivor,
  `Program.Sessions.cs:1552`).
- **`session swap [--target <session or pane>]`** — exchanges the two panes: order reversed, axis
  kept, the ratio SEQUENCE kept (the left/top box stays the size it was; the contents change
  places), focus follows the pane, overlays/scratch/quick untouched (they are session-wide until P5),
  status untouched (aggregated order-independently — `StatusAggregate.cs:24-55`), every id
  untouched. Reply `{"session","paneIds":[…],"focusedPane","axis"}` (`OkRaw`). A single-pane session
  is refused.

## Constraints

- **Do not touch `tests/conformance/control-api.json`.** The `session split on --axis horizontal`
  step (result string = a pane id), a `session split close` step, a `session swap` step (object
  with `paneIds`), and the two refusals (`split close` on a single pane; `swap` on a single pane)
  land in the sibling contract PR after this merges — #235 after #233.
- **`session split off` must keep answering a bare string** — the existing conformance step is a
  type check on it. Every `session split` reply is a string (a pane id); only `swap` is an object.
- **Additive only**: one new key (`SessionState.Axis`, nullable, written only when horizontal so a
  vertical tree still saves the exact bytes today's build saves — `PreP3File_RoundTripsByteForByte`
  and `InMemoryTree_SerializesToThePreP3Bytes` stay green untouched), appended at the END of
  `SessionState` (the "property order is the file's key order" rule, `RestoreState.cs:28`); `axis`
  on the tree inside the split block; `SessionSnapshot.Axis` at the end.
- **Validated on load**: `RestoreState.LoadAxis(string?)` accepts exactly `vertical` /
  `horizontal` (case-sensitive, the wire spelling); anything else, and absent, is vertical.
- **Pane ids are durable and never reassigned** — by a split, a close, a swap, or a restore. A
  restore uses the saved ids verbatim; `CreateSession` accepts the pane-0 id separately from the
  session id. A `session new` still mints pane 0 = session id.
- **Two panes per session.** The axis is per session; a restore file with more than two panes
  restores the first two and logs the rest as dropped (say so in the format comment). N-generality
  in `PaneLayout` may stay; nothing new may depend on it.
- **No pty-host protocol change, no ABI change** (`tools/check-abi.ps1` v18 both sides).
- **Refusals leave the world untouched**; every host method that answers with state uses
  `InvokeOnUiQueued` and re-resolves inside the hop; a failed post or a closed window is a refusal
  (the #234 wording: a timeout leaves the action queued and says so).
- **Refusal logic and reply shapes live in `Agwinterm.Pty`** where the fake exercises them
  (`SplitAxes` for the axis words and their refusal; `SwapReply` for the object) — the
  `SidebarWidths` / `RestoreCaptureReply` shape.
- **#230 invariants above are non-negotiable**; the fake's split must mint an id (`AddPane`) or the
  returned id is untestable.
- Cross-cutting safety rules from `qa/product.md` in full: sandbox instance (`--pipe` and
  `--app-id`), never `keybd_event` / `SendInput`, `PrintWindow` never `CopyFromScreen`, never the
  real profile, `Restart-Sandbox` only under a minted sandbox app-id.

## Technical Details

- **Why the reply stays a string.** The conformance file's `split off` step is a `"result":"string"`
  type check; a pane id is a string, so the change is invisible to the contract while giving the
  caller the handle it lacked. An object would have broken a shipped step for a field (`axis`)
  the tree already carries.
- **Why `on` when already split returns the existing id.** lite's rule, and the only honest
  answer that is also useful: `ok:true "split"` for a no-op was the P2 defect class, and a refusal
  would make every "make sure this session is split" script branch on an error.
- **Why the axis is per session and two panes are the cap.** agterm's model (primary + split), our
  `SplitPane` guard, and the ratio semantics all assume two; a per-pane axis is a tree layout,
  which is not the item. Restore tolerating three panes today is an accident, now a documented
  drop.
- **Why the ratio sequence is kept on a swap.** `Pane.Ratio` is each pane's own share, so reversing
  the panes alone makes a 70/30 into a 30/70 — the layout jumps. agterm says "axis and divider
  ratio remain fixed"; keeping the sequence (exchanging the two panes' values) is that rule in our
  representation.
- **Why ids never move.** Our peer tooling addresses panes by id (the tracker's own words). An id
  that changed meaning on a swap would be a handle that lies. The cost is one relaxed invariant —
  the session id may sit on either side — which the resolver's exact-pane-first order already
  handles, and which restore must honour by never re-minting pane 0's id.
- **Why `split close` on a single pane refuses.** `session close` exists; a `split close` that
  quietly closed the session would be the silent-success class one verb over.
- **Why the accent bar moves for horizontal only.** For vertical the existing pixels are the
  contract of every capture and screenshot so far; for horizontal a bar pinned to the title bar
  would mark the wrong pane half the time.
- **agterm's `off` hides; ours destroys** — unchanged, pre-existing, recorded. `split close` is
  agterm's destroying verb and ours; the difference is only what `off` does.
